# Screen Time Guardian 需求文档

更新时间：2026-08-02  
当前目标版本：1.0.9

## 1. 项目概述

Screen Time Guardian，简称 STG，是一个跨平台屏幕用时守护应用。应用目标是在 macOS、Windows、iOS/iPadOS、Android 上记录屏幕用时，提醒用户休息和切换姿势，并通过本地优先的 P2P 同步机制在多设备之间汇总数据。

应用应以实际可用的桌面或移动端体验为目标，而不是只提供工程骨架。各平台功能、数据结构、同步机制、图标、主要界面和关键交互规则应尽量一致。

## 2. 目标平台

- macOS：菜单栏应用。
- Windows：系统托盘应用，功能与 macOS 对齐。
- iOS/iPadOS：SwiftUI 应用，接入 Screen Time 相关能力。
- Android：Android 应用，需要支持屏幕用时记录和跨平台同步。

## 3. 版本与品牌

- 当前目标版本号为 `1.0.9`。
- 各平台应用图标应统一设计，使用“盾牌 + STG 字样”。
- 应用菜单或关于窗口中应显示应用名、版本号、开发者和免费使用信息。
- 关于窗口应增加使用说明：本应用使用 P2P 同步用户不同设备以统计总屏幕使用时间；各平台应设置统一同步码且建议不要使用默认同步码；本应用不使用云端数据，所有数据保存在本地；只有用户同意的设备才会同步。

## 4. 核心功能需求

### 4.1 屏幕用时记录

- 应用需要记录屏幕使用会话，包括设备 ID、设备名称、平台、开始时间、结束时间、时区、持续时间、停止原因、心跳时间、更新时间和修订号。
- 屏保、屏幕关闭、锁屏、待机、睡眠、关机、退出应用时，应结束当前会话并保存屏幕用时数据。
- 从锁屏、睡眠、待机等状态恢复后，应重新开始会话，并重启护眼提醒周期；姿势切换由该周期的偶数次提醒触发。
- 运行中应定期刷新当前会话心跳和持续时间，避免异常退出后丢失过多数据。
- 跨设备计算每日、区间和每周总用时时，应对多个设备重叠使用的时间段做并集去重，避免同一时间同时使用电脑和手机时被重复累计到总用时。
- 各设备自己的用时统计仍按设备单独累计，不能因为总用时去重而丢失设备级明细。

### 4.2 护眼和姿势提醒

- 护眼提醒默认每 3 分钟触发，并可在设置中调整。
- 姿势切换不再使用独立定时器，也不再单独设置姿势切换分钟数。
- 姿势切换只保留开关。开关打开时，提醒周期与护眼提醒合并：
  - 第 1 个护眼周期提醒：只提醒看 20 英尺外 20 秒。
  - 第 2 个护眼周期提醒：提醒姿势切换，同时提醒看 20 英尺外。
  - 后续按奇偶护眼周期循环。
- 姿势切换间隔始终按护眼间隔的 2 倍计算，默认 6 分钟。
- 如果姿势切换开关关闭，则所有护眼周期都只触发护眼提醒。
- 提醒弹窗必须有明确关闭按钮。
- 普通模式下，提醒弹窗应有倒计时，倒计时结束后才能关闭。
- 会议模式是唯一允许立即关闭提醒的状态。会议模式开启时，提示文案固定为“会议模式：可以立即关闭”；会议模式关闭时，不得显示会议模式文案。
- 会议模式下只显示提醒，不播放提醒声音；非会议模式下，移动端提醒应在用户已授权的前提下播放声音。
- iOS 和 Android 的提醒倒计时必须基于绝对可关闭时间计算，而不是仅靠前台页面每秒递减。应用退到后台、锁屏或熄屏后再回来，应按真实经过时间更新剩余秒数。
- 触发提醒时，应结束当前用时会话并记录对应停止原因，提醒关闭后开始新会话。

### 4.3 每日计划与超时提醒

- 每日计划默认应为 480 分钟，即 8 小时。
- 设置中每日计划应按“小时 + 分钟”输入，例如 `8 小时 0 分钟`，不能只显示分钟数，也不能只有加减按钮。
- 内部存储和同步仍使用总分钟数 `planned_daily_minutes`。
- 当当天屏幕总用时超过计划值时，应弹出超时提醒。
- 超时提醒使用与护眼提醒相同的关闭规则：会议模式开启可立即关闭；会议模式关闭必须等倒计时结束后才能关闭。
- 超时提醒需要节流，同一天内短时间重复超过计划时不应连续弹窗，建议间隔 25 分钟。
- 每周一应提示上周用时总结，并允许设置本周每日计划用时。

## 5. 报告需求

### 5.1 日报

- 报告窗口应支持按日期查看日报。
- 日报应显示当天去重后的总用时。
- 日报应显示当天各设备分别用时，便于查看 macOS、Windows、iOS/iPadOS、Android 各自贡献。
- 日报应列出当天各时间段明细，包括开始、结束、时长、停止动作、平台、设备和数据范围。
- 日报明细应使用表格或等价的对齐布局展示，列宽稳定、文本不挤在一起。
- 打开报告时，应结束当前会话并记录停止原因，关闭报告后重新开始会话。

### 5.2 多日报

- 报告窗口应支持选择开始日期和结束日期查看多日报。
- 多日报应显示区间去重后的总用时、每天平均用时，以及每天用时列表。
- 多日报应显示区间内各设备分别用时。
- 多日报也应使用表格或等价的对齐布局展示关键列。
- iOS/iPadOS 和 Android 报告页内容较长时必须可以上下滚动，不能被固定视图塞满。

### 5.3 跨平台周统计

- 报告中必须显示上周平均每天屏幕总用时。
- 报告中必须汇总所有平台同步后的去重总用时。
- 报告中必须显示各平台各自的上周总用时和平均每天用时。
- 平台名称应标准化为 macOS、iOS、iPadOS、Windows、Android、Unknown。
- 周统计应同时保留设备级明细，避免用户只能看到平台汇总而看不到具体设备。

### 5.4 数据范围与来源

- 本应用本机计时数据和 P2P 同步来的其它设备数据都应进入同一报告体系。
- iOS/iPadOS 通过 Screen Time 全活动阈值产生的用时记录，应进入本应用日报、多日报、周报，并通过 P2P 同步给其它平台。
- 报告中应能区分数据范围，例如本机屏幕会话、iOS Screen Time 系统记录等。

## 6. P2P 同步需求

### 6.1 同步方式

- 不再使用用户选择的网盘目录同步。
- 应改为本地优先 P2P 同步。
- 各平台应使用统一的同步协议、数据结构、配对逻辑和冲突处理规则。
- 同步内容至少包括屏幕用时会话数据，并能在各平台报告中汇总显示。
- 同步机制必须跨 macOS、Windows、iOS/iPadOS、Android 一致，不能出现某个平台只显示“发现设备”但数据结构或信任机制不同导致无法互通。

### 6.2 局域网发现与传输

- 局域网发现统一使用 Bonjour/DNS-SD：`_stg-sync._tcp.local`，底层为标准 mDNS UDP `5353`。
- macOS、iOS/iPadOS、Windows、Android 都应发布并浏览同一个 Bonjour 服务类型。
- 数据传输使用 TCP，端口由 Bonjour SRV 记录动态通告。
- TCP 帧使用 4 字节 big-endian 长度前缀。
- 传输内容必须加密。

### 6.3 配对与加密

- 每台设备有 6 位数字 P2P 配对码；各平台必须用相同规范化规则，只保留数字，不足 6 位时右侧补 `0`，超过 6 位时只取前 6 位。
- 使用同一配对码的设备可以互相发现，但不能自动同步数据。
- 配对码用于派生 AES-GCM 加密密钥。
- 发现包和加密信封中应包含配对校验信息，用于避免处理不同配对组的数据。

### 6.4 设备确认

- P2P 设置中应显示发现到的设备。
- 每个发现设备应有状态：待确认、已同意、已拒绝。
- 用户必须能对配对设备执行“同意”或“拒绝”。
- 只有已同意设备可以发送和接收同步快照。
- 已拒绝设备应被忽略，除非用户后续重新同意。
- 未同意设备发来的数据不能导入本地数据库，也不能只因为配对码一致就自动同步。
- 已同意设备应被持久保存。设备换 Wi-Fi、IP 变化、应用重启后，不应反复消失并要求重新同意。
- 如果发现同一真实设备出现多个旧临时 ID，应优先用稳定设备 ID 合并或继承已有信任状态，避免设置页出现一串同名设备。

### 6.5 手动同步与定时同步

- P2P 设置中应提供“立即同步”入口。
- P2P 设置中应允许配置同步间隔。
- 定时同步只应同步已同意设备。
- 如果没有已同意设备，应给出明确状态提示。

### 6.6 同步效率、兼容与历史数据

- 同步协议应支持能力协商；设备应在 Bonjour TXT、加密信封和同步快照中声明能力。
- `1.0.9` 当前实际启用能力为 `delta_sync`、`gzip` 和 `history_compaction`。
- 新版本设备之间应优先使用增量同步：基于每个已同意设备的 `last_sync_at_utc`，只发送该时间之后更新的会话和删除墓碑，并保留小幅重叠窗口避免边界遗漏。
- 新版本设备之间应支持 gzip 压缩加密载荷；未声明 gzip 能力的旧设备继续使用普通 JSON 载荷。
- 同步协议应为 `weekly_manifest`、`daily_summary`、`history_compaction`、`tombstone_ack` 保留兼容能力字段，后续扩展不能破坏旧版本读取。
- 能力协商不仅用于单次传输格式选择，也必须用于历史数据处理判断；在对端未声明相关历史能力或未确认历史窗口前，本机不能假设对端已经具备摘要读取、墓碑确认或历史压缩能力。
- 当前周和上一周应保留详细 `screen_session` 明细。
- 上上周及更早的数据可生成本地历史归档和周摘要；历史归档不参与 P2P 同步。
- `1.0.9` 阶段只生成本地历史归档和周摘要，不自动从活动 `sessions.json` 中物理删除明细。
- 在所有报告路径都能读取摘要、并且可信设备都确认相关历史窗口前，不应自动物理删除仍被报告依赖的明细。

### 6.7 设备身份

- 每台设备应有稳定的 `device_id`。
- `device_id` 应在更换 Wi-Fi、IP 变化、应用重启后保持不变。
- 重装应用后也应尽量保持不变，前提是平台提供稳定设备标识或本地应用数据未被彻底清除。
- 各平台建议使用的稳定来源：
  - macOS：host UUID，再持久化到本地 `device_id`。
  - iOS/iPadOS：`identifierForVendor`，再持久化到本地 `device_id`。
  - Windows：MachineGuid 派生 UUID，再持久化到本地 `device_id`。
  - Android：Android ID 派生 UUID，再持久化到本地 `device_id`。

## 7. 设置需求

- 所有对话框或设置窗口必须有关闭、取消或保存按钮。
- 设置中分钟类字段必须支持直接输入数字。
- 每日计划用时必须按小时和分钟拆分输入。
- 设置中应包含：
  - APP 语言。
  - 设备名称。
  - 姿势切换开关。
  - 每日计划用时。
  - 会议模式。
  - 系统启动时自动启动。
  - 跟踪对象。
  - P2P 同步开关。
  - P2P 配对码。
  - P2P 同步间隔。
  - P2P 设备同意和拒绝。
  - 数据目录或本地存储位置说明。
- macOS 应允许查看并设置本地数据目录。默认目录可以是应用相关目录，但设置界面应让用户知道当前实际保存位置。
- iOS/iPadOS 和 Android 应在设置中显示通知、声音、悬浮窗或系统 Screen Time 相关权限状态，并提供跳转到系统设置的入口。
- 语言切换后，界面文字应立即按所选语言刷新，不能只保存值而不更新界面。

## 8. 跟踪功能需求

- 应提供“跟踪”入口。
- 当前跟踪对象为 LLM Ranking。
- 跟踪窗口应显示 OpenRouter 本周 prompt token Top 20。
- 应优先读取本周本地缓存。
- 缓存不存在或用户点击刷新时，应从 OpenRouter 获取数据并保存缓存。
- 表格字段应包括排名、LLM 名字、Prompt Tokens、Output Tokens、Input Price / 1M、Output Price / 1M、Weekly Revenue。
- 表格列标题应支持点击排序。
- 同一列重复点击时，应在升序和降序之间切换。
- 排序逻辑应按字段真实类型排序：数字列按数字排序，文本列按文本排序，不能把数字当字符串排序。
- iOS/iPadOS 跟踪表格横向滚动、排序和关闭按钮不能互相阻塞，点击多列排序后仍应能横向滚动并关闭页面。

## 9. 平台一致性需求

### 9.1 macOS

- 应作为菜单栏应用运行。
- 菜单应包含报告、设置、跟踪、关于、退出。
- 应处理屏幕睡眠、系统睡眠、锁屏、唤醒、退出等生命周期。
- P2P、报告、设置、跟踪、提醒和计划功能应作为其它平台对齐基准。

### 9.2 Windows

- 应作为系统托盘应用运行。
- 菜单应与 macOS 对齐：报告、设置、跟踪、关于、退出。
- 设置界面应参考 macOS 功能项。
- 报告、跟踪、P2P、提醒、计划、自启动等功能应与 macOS 对齐。
- 应能编译生成 Windows exe。

### 9.3 iOS/iPadOS

- 应使用 Apple Screen Time 合规能力记录和展示用时，包括 FamilyControls、DeviceActivity 和 DeviceActivityReport。
- iOS/iPadOS 通过不指定应用、类别和网站过滤条件的 DeviceActivity 阈值记录系统 Screen Time 全活动范围；受 Apple API 限制，仍不能保证第三方完整获取所有任意屏幕点亮时间。
- DeviceActivity 阈值事件应写入 App Group 共享事件日志，再由主应用导入成本应用 `screen_session` 记录。
- Screen Time 阈值应按可配置 checkpoint 间隔记录增量片段，默认 2 分钟；每累计到护眼周期触发一次提醒，不能把连续阈值再次从 0 开始导入造成重叠。
- `1.0.9` 暂不调整 iOS Screen Time 计时模型；本轮只补齐通知国际化、同步协议、历史归档和跨平台口径。
- 导入的 iOS Screen Time 数据应参与本地报告，并通过 P2P 同步到其它平台。
- iOS 超时后不得限制、屏蔽或阻止任何 App，只能按提醒规则提示用户。
- 需要支持 P2P 同步、设置、报告和跟踪。
- 真机能力涉及 Family Controls、DeviceActivity、Bonjour/local network 等权限时，应在工程和签名配置中明确；同步发现应优先使用 Bonjour，避免依赖需要额外申请的 Multicast Networking entitlement。
- 首次启动时，应在系统允许的范围内请求通知 alert、badge、sound 权限和 Screen Time 授权。
- 设置中应显示通知授权、横幅/提醒、声音、提醒样式、时间敏感等状态，并提供打开系统设置的按钮。
- iOS 的持续横幅样式由用户在系统设置中控制，应用不能强制设置；需求上应在设置页说明并提供跳转。
- iOS 应在前台用应用内弹窗提示；在后台或其它应用中依赖系统通知。
- iOS Screen Time 扩展发出的系统通知应跟随应用语言设置进行国际化。
- iOS 超时或休息提醒的倒计时应按真实时间计算，即使应用后台、锁屏或屏幕关闭也应继续经过。

### 9.4 Android

- 应具备 Android 项目和实际应用实现，而不是只有其它平台。
- 应支持屏幕用时记录、P2P 同步、设置、报告、跟踪、护眼提醒、姿势切换提醒、每日计划提醒和关于信息。
- 应使用前台服务保持后台计时，并结合 Usage Stats、交互状态、屏幕开关、关机广播等信息记录会话。
- 应支持通知权限、Usage Stats 权限、悬浮窗权限、忽略电池优化设置入口，并在设置页显示关键权限状态。
- Android 13+ 应请求 `POST_NOTIFICATIONS` 运行时权限。
- 非会议模式提醒使用高重要性有声通知通道；会议模式提醒使用静音通道。
- 提醒弹窗优先使用悬浮窗；无悬浮窗权限时应打开提醒 Activity，并同时发通知。
- 需要补齐可复现构建方式，例如 Gradle wrapper 或明确构建说明。

## 10. 错误与体验要求

- macOS 运行一段时间后不应无响应。
- P2P 后台队列不应阻塞 UI。
- Bonjour 发现、解析和同步传输不应阻塞 UI 线程。
- 报告、设置、跟踪窗口打开后，排序、滚动、关闭等交互不应长时间无响应。
- 英文界面下提醒弹窗文字必须完整显示，不能被按钮或窗口边界截断。
- 手机通知不能只提醒一两次后就停止；只要监控仍开启且满足触发条件，应持续按规则触发。
- 屏幕关闭、待机、锁屏、睡眠后，计时不能继续无上限累计；恢复后应重新开始新的会话和提醒周期。
- iOS/macOS 键盘或系统触觉相关警告，例如缺失 `hapticpatternlibrary.plist`，不应影响应用主流程；如能规避，应避免触发相关系统错误。
- 构建产物时间和版本号应能明确验证，不能声称已更新但文件仍是旧时间。

## 11. 构建与产物要求

- macOS 应能生成 `.app`。
- Windows 应能生成 `.exe`。
- iOS/iPadOS 应能通过本地无签名编译验证，真机签名能力另行配置。
- Android 应能通过 Gradle 构建生成 debug APK。
- 版本号、应用图标和关于信息应与目标版本一致。
- 当前版本 `1.0.9` 的产物应能通过构建时间、Info.plist、csproj、Gradle versionName/versionCode、关于窗口等方式验证。
- Windows 发布包应优先使用依赖 .NET 8 Desktop Runtime x64 的 framework-dependent 模式，以缩小目标程序体积。
- Windows 目标机器缺少 .NET Desktop Runtime 时，应由 .NET apphost 检测并提示缺失运行库和 Microsoft 安装链接；文档中也应明确提供安装链接。

## 12. 验收标准

- 四个平台项目均存在，并有清晰构建入口。
- macOS、Windows、iOS/iPadOS、Android 的主菜单或主入口、设置、报告、跟踪、提醒、计划和 P2P 功能口径一致。
- 任一平台记录的屏幕会话，经 P2P 同步后，能在其它平台报告中汇总显示。
- iOS/iPadOS Screen Time 监控范围产生的记录，也能进入本应用报告并同步到其它平台。
- P2P 发现统一为 Bonjour 服务 `_stg-sync._tcp.local`，传输端口通过 SRV 记录动态通告。
- `1.0.9` 设备之间应能声明 `delta_sync`、`gzip`、`history_compaction` 能力，并据此使用增量同步和 gzip 加密载荷；旧设备仍可回退到完整 JSON 快照。
- 未同意设备不能同步数据。
- 上上周及更早记录应能写入本地历史归档和周摘要；当前版本不应自动删除活动明细。
- 屏保、睡眠、锁屏、关机或退出后，屏幕用时数据不会丢失，并且恢复后定时器会重新启动。
- 所有弹窗可关闭，会议模式才允许立即关闭；普通模式必须等倒计时结束。
- 每日计划按小时和分钟输入，设置数值可直接键盘输入。
- 报告包含上周去重总平均、各平台平均、各设备分别用时和时间段明细，并以表格或等价对齐布局展示。
- 跟踪表格列可点击排序，重复点击同一列能在升序/降序之间切换。
- iOS Screen Time 扩展发出的系统通知应随应用语言切换为中文或英文。
- Windows exe、macOS app、Android APK、iOS Debug app 的产物时间、版本号和图标可验证。
